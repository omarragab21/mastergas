# تقرير العمل والاختبارات اليومية — Admin APIs

**التاريخ:** 2026-10-12  
**المشروع:** Mastergas Admin  
**البيئة:** `https://backend-tijara.be-kite.com/api/v1`  
**المصدر المرجعي:** `Tijara-New-App.postman_collection.json`  
**النطاق:** Categories، Products، Product Attributes، Discount Codes

## 1. الملخص التنفيذي

تم ربط واختبار وحدات إدارة الكتالوج داخل لوحة التحكم، وتشمل:

- إدارة الأقسام والأقسام الفرعية.
- إدارة المنتجات وربط المنتج بالقسم عن طريق `category_id` و`subcategory_id`.
- إدارة خصائص المنتجات وقيمها.
- إدارة أكواد الخصم والعروض.
- دعم الصور والحقول متعددة اللغات والـ pagination.
- إضافة طلبات صريحة من لوحة التحكم لجلب العناصر النشطة وغير النشطة.

الواجهة والاختبارات المحلية ناجحة. لكن اختبار الإنتاج أثبت أن الـ API المنشور يستبعد العناصر غير النشطة من قوائم الـ collection حتى عند إرسال معاملات طلب مخصصة لذلك؛ لذلك يلزم تعديل Tijara Backend نفسه حتى يظهر المنتج/القسم/العرض غير النشط بشكل دائم في القائمة.

## 2. الـ APIs التي تم ربطها

| الوحدة | العمليات المستخدمة | النتيجة |
|---|---|---|
| Authentication | `POST /v1/login`، `POST /logout` | تسجيل دخول Admin وإدارة الجلسة |
| Categories | `GET/POST/PUT/DELETE /v1/categories` | CRUD للأقسام والأقسام الفرعية |
| Products | `GET/POST/PUT/DELETE /v1/products` | CRUD للمنتجات والرفع متعدد الصور |
| Product Attributes | `GET/POST/PUT/DELETE /v1/attributes` | CRUD للخصائص |
| Attribute Options | `POST/PUT/DELETE /v1/attributes/{id}/options` | إدارة قيم الخصائص والألوان |
| Discount Codes | `GET/POST/PUT/DELETE /v1/discount_codes` | CRUD لأكواد الخصم والعروض |

## 3. الأعمال التي تم تنفيذها في المشروع

### المنتجات

- ربط المنتج بالقسم الرئيسي والفرعي عبر `category_id` و`subcategory_id`.
- الحفاظ على `category_id` عند التحديث.
- دعم الصور كـ `images[]` في طلبات `multipart/form-data`.
- معالجة الحالة `active/inactive` وعرض badge الحالة.
- جمع كل صفحات المنتجات عند حساب إحصائيات الأقسام.
- منع الاعتماد على صفحة API واحدة فقط.

### الأقسام

- دعم الأقسام الرئيسية والأقسام الفرعية.
- حساب عدد المنتجات المرتبطة بالقسم من قائمة المنتجات الفعلية.
- تحميل كل صفحات المنتجات لحساب العدد بدقة.
- عرض الحالة النشطة وغير النشطة في الواجهة عند توفرها من الـ API.

### خصائص المنتجات

- ربط الخصائص بالـ Admin API.
- دعم نوع النص واللون.
- تحويل نوع النص إلى النوع المدعوم من Tijara عند الإرسال.
- فصل إنشاء الخاصية عن إنشاء قيمها.
- دعم إنشاء وتعديل وحذف قيم الخصائص.
- عدم إرسال `options` أثناء تعديل اسم أو نوع الخاصية حتى لا يتم استبدال القيم الحالية.

### العروض وأكواد الخصم

- ربط CRUD الخاص بـ `/v1/discount_codes`.
- حساب الحالة من `is_active` و`start_date` و`end_date`.
- دعم حالات: نشط، متوقف، منتهي، مجدول.
- تحميل كل صفحات أكواد الخصم بدل الاكتفاء بالصفحة الأولى.

## 4. إصلاح مشكلة ظهور الحالات

تم تحديث طبقة الـ Admin لتضمين المعاملات التالية في قوائم المنتجات والأقسام والعروض:

```text
include_inactive=1
show_all=1
```

كما تم تعديل خدمة الـ pagination بحيث تحافظ على هذه المعاملات في كل صفحة يتم طلبها، وتم تعديل إحصائيات المنتجات لتجميع كل الصفحات.

الملفات الرئيسية المتأثرة:

- `admin/src/application/adminCatalogService.js`
- `admin/src/views/ProductsView.vue`
- `admin/src/views/CategoriesView.vue`
- `admin/src/views/DiscountsView.vue`
- `tests/adminCatalogQA.test.js`

- `git diff --check` ناجح.

### اختبارات الإنتاج بالـ API

- تسجيل دخول Admin: ناجح، HTTP `200`.
- قائمة المنتجات بدون فلترة: رجعت 5 منتجات نشطة فقط.
- طلب `is_active=0`: لم يُرجع المنتجات غير النشطة.
- طلب `status=inactive`: لم يُرجع المنتجات غير النشطة.
- طلب `include_inactive=1`: لم يُرجع المنتجات غير النشطة.
- طلب `show_all=1`: لم يُرجع المنتجات غير النشطة.
- المنتج رقم `15` موجود فعلًا وحالته `is_active=false` عند طلب التفاصيل، لكنه غير موجود في قائمة المنتجات.

## 6. المشاكل المكتشفة في الـ APIs

### مشكلة عالية — قوائم المنتجات تستبعد العناصر غير النشطة

المنتج غير النشط يظل موجودًا في قاعدة البيانات ويمكن فتحه بالتفصيل، لكن endpoint القائمة لا يعيده. هذا يجعل المنتج يختفي من شاشة الإدارة بعد تعطيله.

**الأثر:**

- لا يمكن رؤية المنتج غير النشط من قائمة المنتجات.
- لا يمكن حساب عدد المنتجات في القسم بدقة من القائمة الحالية.
- فلاتر active/inactive لا تعمل بشكل موثوق من جهة الـ API.

**المطلوب من Tijara Backend:**

- جعل endpoint إدارة المنتجات يعيد كل الحالات افتراضيًا، أو
- إضافة معامل موثق مثل `include_inactive=1` يعمل فعليًا، مع دعم `is_active=0` و`is_active=1`.

### مشكلة محتملة — الأقسام والعروض

تم تجهيز الواجهة لجلب كل الحالات في الأقسام والعروض، لكن يجب التأكد من الـ Backend بعد وجود سجل غير نشط فعليًا؛ لأن سلوك المنتجات الحالي يثبت أن بعض قوائم الـ API قد تطبق active scope افتراضيًا.

### مشكلة عالية — أخطاء المصادقة ترجع HTTP 500

طلبات بدون token أو بـ token غير صالح ترجع `500` بدل `401`، وقد تحتوي على تفاصيل Laravel داخلية مثل `exception` و`file` و`trace`.

**التوصية:** إرجاع JSON مختصر بحالة `401` وتعطيل تفاصيل الأخطاء في الإنتاج.

### مشكلة عالية — endpoint المستخدمين يعتمد على جدول packages غير موجود

إنشاء مستخدم بصلاحياته الكاملة أدى إلى خطأ قاعدة بيانات بسبب عدم وجود جدول `packages`.

### ملاحظات متوسطة

- إنشاء خاصية مع `options: []` مقبول حاليًا؛ يجب توثيق هل هذا مسموح أم إضافة حد أدنى للقيم.
- تحديث خصم بقيمة صفر مرفوض؛ يجب تحديد هل `0` معناه إزالة الخصم أم لا.

## 7. جودة Postman Collection

- متغيرات `base_url` و`version` و`token` غير مضبوطة داخل الملف.
- بعض الطلبات تستخدم IDs ثابتة، مما يجعل التشغيل معتمدًا على ترتيب البيانات.
- بعض ملفات الصور تشير إلى `postman-cloud://` وغير متاحة محليًا.
- يوجد اسم field في طلب منتج يحتوي على newline في نهايته.
- يوجد تكرار في `shipping_info_en[1]`.
- اختبارات Postman المدمجة لتسجيل الدخول غير مفعلة بالكامل.
- لا توجد teardown scripts كافية لتنظيف البيانات التجريبية تلقائيًا.

## 8. حالة التسليم

التغييرات البرمجية موجودة على `origin/main`:

- **Main:** `0771a97` — forward inactive and show-all status parameters.
- **Admin:** `f04de8a` — pass inactive and show-all parameters to list services and views.

الـ Admin جاهز من ناحية الكود والاختبارات، لكن الإغلاق الكامل للمشكلة يتطلب تعديل Tijara Backend المنشور حتى يعيد العناصر غير النشطة من قوائم الـ API.

## 9. التوصية النهائية

لا يُعتبر سيناريو active/inactive مغلقًا إنتاجيًا قبل تنفيذ اختبار إعادة الاختبار التالي على الـ Backend:

1. إنشاء منتج نشط.
2. التأكد من ظهوره في قائمة المنتجات.
3. تحويله إلى غير نشط.
4. التأكد من بقائه في القائمة مع badge غير نشط.
5. التحقق من ظهوره في القسم المرتبط.
6. تكرار السيناريو مع عرض/كود خصم وقسم.
7. التأكد من أن واجهة المستخدم تستطيع إعادته إلى active بدون فقدان السجل.

**الحكم النهائي:** تكامل الـ Admin واختباراته المحلية ناجحان، أما سبب اختفاء العناصر غير النشطة في الإنتاج فهو من contract/implementation الخاص بقوائم Tijara API ويحتاج إصلاحًا في الـ Backend.
